Diagrama de flujo de ataque

Flujo 1 — Bypass de licencia
Atacante instala plugin
Servidor de licencias caído / red cortada
❌ ANTES: cualquier clave era válida offline
✅ CORREGIDO: offline solo con caché previo válido
Flujo 2 — Exposición de credenciales
Cliente accede al plugin WP
❌ ANTES: menú "Base de datos" visible
Ve host, usuario, password, tablas
Puede "Resetear contraseña admin WP"
✅ CORREGIDO: menú eliminado del frontend
Flujo 3 — Upload malicioso
Usuario sube archivo adjunto
⚠️ upload.php — validación de extensión solo en cliente
Sube shell.php como shell.php.jpg o con MIME falso
Ejecuta comandos en el servidor
🔧 PENDIENTE: validar en servidor + mover uploads fuera de webroot
Flujo 4 — HMAC hardcodeado
Atacante descarga plugin ZIP
Lee HMAC_SECRET en class-luna-license.php
Levanta servidor falso de licencias
Forja respuestas HMAC válidas → bypass de pago
🔧 PENDIENTE: mover secret a WP option cifrada / env var

Autenticación y Licencias

CorregidoOffline fallback sin validación
Cuando el servidor era inalcanzable, cualquier clave era aceptada como válida con plan "offline".
Solo se acepta modo offline si existe caché previo de verificación exitosa real.
class-luna-license.php → verify()
AltoHMAC_SECRET hardcodeado en código fuente
El secreto compartido entre cliente y servidor está en texto plano en el ZIP distribuido. Cualquiera que obtenga el plugin puede fabricar respuestas firmadas válidas y crear su propio servidor de licencias.
Almacenar en WP option cifrada o variable de entorno del servidor; leer en runtime, nunca en código.
class-luna-license.php:10 / luna-license-server.php:18
MedioToken de entrada al admin almacenado en texto plano
El token de acceso directo al panel (para botón en Plesk) se guarda como WP option sin cifrar. Si la DB es comprometida, el atacante obtiene acceso directo.
Guardar hash SHA-256 del token; comparar con hash_equals en verificación.
class-luna-activator.php → generate_entry_token()
MedioSin rate limiting en verificación de licencias (cliente)
El plugin puede intentar verificar claves repetidamente sin ningún backoff. Facilita fuerza bruta de claves si el servidor no limita.
El servidor ya retorna HTTP 429; el cliente debería respetar el header Retry-After y bloquear reintentos por 5 minutos.
class-luna-license.php → verify()

Upload de Archivos

CríticoUpload de archivos PHP ejecutables (RCE)
upload.php solo valida la extensión del nombre original enviado por el cliente. Un atacante puede subir shell.php renombrándolo shell.jpg o manipulando el Content-Type. Si el directorio /uploads/ es accesible desde el navegador, puede ejecutar código arbitrario en el servidor.
1) Validar MIME real con finfo_file(). 2) Renombrar todos los archivos a UUID + extensión permitida. 3) Mover /uploads/ fuera del webroot o agregar php_flag engine off en .htaccess. 4) Lista blanca estricta de extensiones (solo imágenes, docs, PDF).
luna-workspace/app/api/upload.php
AltoRuta de uploads predecible + sin autenticación en archivos
Los archivos subidos son accesibles directamente por URL sin verificar si el usuario que los solicita tiene acceso al workspace correspondiente. Cualquier persona con la URL puede descargar adjuntos privados.
Servir archivos a través de un endpoint PHP autenticado que valide pertenencia al workspace antes de enviar el stream.
luna-workspace/app/uploads/ (directamente servido por Apache)

APIs PHP del Backend

AltoConfiguración DB expuesta en config.php
config.php contiene credenciales de base de datos en texto plano. Si el servidor devuelve PHP como texto plano (falla de mod_php) o hay un path traversal, las credenciales quedan expuestas. El archivo está dentro del webroot.
Mover config.php fuera del webroot (ej: /var/www/luna-config.php) y referenciarla con ruta absoluta, o usar las constantes de WP (DB_HOST, DB_USER, etc.) que ya están disponibles.
luna-workspace/app/config.php
AltoSQL queries con interpolación directa en algunas rutas
Algunos endpoints construyen queries mezclando variables PHP directamente en la cadena SQL en lugar de usar siempre $wpdb->prepare() o PDO con parámetros. Si el dato viene del usuario, es inyección SQL potencial.
Auditar todos los endpoints y reemplazar cualquier "$wpdb->query("...{$var}...")" por $wpdb->prepare() con marcadores de posición.
luna-workspace/app/api/kanban.php, workspaces.php
MedioSin CSRF protection en APIs stateless
Los endpoints PHP usan un token en config.php pero las peticiones cross-site podrían ser enviadas desde otro dominio si el navegador incluye las cookies. No hay verificación de Origin o nonce por request.
Agregar header X-Requested-With verificado en el servidor, o implementar CSRF token por sesión.
luna-workspace/app/api/*.php
MedioLogs de verificación sin sanitización
La tabla lls_verify_log guarda license_key y domain tal como los envía el cliente, sin límite de longitud ni sanitización extra. Un cliente malicioso podría intentar log injection si los logs son mostrados en algún panel.
Limitar longitud de license_key (max 25 chars) y domain (max 255 chars) antes de insertar. Ya usar $wpdb->insert() es un paso correcto.
luna-license-server/includes/class-lls-db.php → log()

Frontend y XSS

CorregidoExposición de URL del servidor de licencias
El panel de administración del License Server mostraba la URL completa del endpoint REST en la interfaz, facilitando que un atacante apunte un ataque directo al endpoint.
Eliminado de class-lls-admin.php → page_config() y page_list().
luna-license-server/includes/class-lls-admin.php
CorregidoPanel de base de datos expuesto a clientes
El menú "Base de datos" mostraba credenciales DB, estructura de tablas, y tenía botones para "Recrear tablas" y "Resetear contraseña admin WP" accesibles a cualquier usuario del plugin.
Submenú eliminado completamente de register_menu() y render_database_page() removido.
luna-workspace/includes/class-luna-admin.php
BajoXSS en títulos/comentarios sin sanitizar en display
Algunos textos renderizados en el frontend usan esc() correctamente, pero hay algunos lugares donde datos del usuario (nombre de tarea, comentario) podrían ser interpolados sin escape si se agrega nueva funcionalidad.
Mantener y hacer obligatorio el uso de esc() (la función ya existe y escapa HTML) en TODO el renderizado dinámico. Agregar Content-Security-Policy header.
luna-workspace/app/index.html → funciones render*()
BajoSin cabeceras de seguridad HTTP
El .htaccess no establece X-Frame-Options, X-Content-Type-Options, Content-Security-Policy ni Referrer-Policy. Expone a clickjacking y MIME sniffing.
Agregar en .htaccess: Header always set X-Frame-Options "SAMEORIGIN", X-Content-Type-Options "nosniff", Referrer-Policy "no-referrer".
luna-workspace/app/.htaccess
BajoMensajes de error demasiado verbosos al cliente
Algunos endpoints PHP devuelven mensajes de error detallados (ej: tipo de error SQL, stack trace) que pueden ayudar a un atacante a mapear la estructura interna.
En producción, devolver solo mensajes genéricos al cliente y loguear detalles en el servidor con error_log().
luna-workspace/app/api/*.php
